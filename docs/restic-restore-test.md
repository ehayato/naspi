# restic 復元テスト手順書

バックアップは「復元できること」を確認して初めて意味を持つ。この文書は、restic のバックアップが復元できること、
およびスナップショットが元データを漏れなく含んでいることを確認する手順を定める。

プロジェクト計画書の次の項目に対応する。

- 3.2 成功基準: 「バックアップが所定の周期で実行され、復元可能性が確認される」
- 5.3 受入基準: 「復旧時の手順が最低限追跡できること」

## 1. 前提

| 項目 | 内容 |
|---|---|
| コンテナ | `naspi_restic`（`restic/restic`） |
| リポジトリ | コンテナ内 `/backup/repo`（ホストでは `DATA_HDD/repo`） |
| パスワード | `.env` の `RESTIC_PASSWORD`（コンテナの環境変数として渡される） |
| バックアップ対象 | 本番: `/data`（クラウドのローカルコピー）／ 開発: `/config`（動作確認用の小さなディレクトリ） |
| 世代管理 | 日次 7 世代 + 週次 2 世代（`restic/backup.sh`） |

開発モードでバックアップ対象が `/config` なのは、rclone の FUSE マウント（クラウド全体）を読みにいくと、
非常に遅く（実測で約 0.8MB/s）、ディスクも圧迫するため。

## 2. テストスクリプトの実行

```
docker exec naspi_restic sh /config/restore-test.sh [オプション]
```

| オプション | 内容 |
|---|---|
| （なし） | ランダムに選んだ 10 ファイルを復元し、元データと照合する |
| `--samples N` | 抽出するファイル数を N にする |
| `--full` | スナップショット全体を復元し、`diff -r` で元データと照合する（小さい対象向け） |
| `--snapshot ID` | 対象のスナップショットを指定する（既定は元データの最新） |
| `--source DIR` | 元データのパスを指定する |

環境変数: `READ_SUBSET`（データ本体を読んで検査する割合。既定 `10%`）、`COVERAGE_MIN_PERCENT`（既定 `99`）、
`SAMPLE_MAX_BYTES`（照合用に抽出するファイルの最大サイズ。既定 20MiB）、`RESTIC_REPOSITORY`。

### 確認する内容

| 手順 | 内容 | 失敗の意味 |
|---|---|---|
| 1/4 整合性 | `restic check --read-data-subset`（構造 + データ本体の一部） | リポジトリの破損 |
| 2/4 対象 | 元データの最新スナップショットを選ぶ | スナップショットが存在しない |
| 3/4 網羅性 | スナップショットの項目数（ファイルとディレクトリ）が、元データの 99% 以上か | **バックアップが途中で中断された**、または元データが更新された |
| 4/4 復元と照合 | 一時ディレクトリへ復元（`--verify`）し、元データと比較する | 復元不能、または内容の不一致 |

- 終了コード: `0` = 成功 / `1` = 失敗あり / `2` = 使い方の誤り。
- 結果は `history/restore-test.tsv` に追記される（開始時刻・`manual`・終了コード・所要秒）。
- 復元先は毎回作成する一時ディレクトリで、終了時に削除される。元の場所には書き込まない。
- 元データがスナップショット後に更新されている場合、その分は「照合できず」になる（失敗にはしない）。
  網羅性が不足した場合は、`/backup` を実行して取り直してから再テストする。

### 例（開発環境）

```
[1/4] リポジトリの整合性チェック（構造 + データの 10%）
  [OK] エラーなし
[2/4] 対象のスナップショット
  [OK] 7bfc5292 (2026-11-21 13:54:19)
[3/4] 元データの網羅性（ファイルとディレクトリの数）
  [OK] スナップショット 4件 / 元データ 4件
[4/4] 復元と照合
  [OK] 復元 3件 / 元データと一致 3件 / 照合できず 0件（元データなし、または更新済み）
[restore-test] 結果: 成功
```

## 3. 手動で行う手順（スクリプトの内部と同じ）

restic はコンテナ内で実行する。`-r /backup/repo` を付ければ、パスワードは環境変数から渡される。

```
docker exec naspi_restic restic -r /backup/repo snapshots                      # 1. 世代の確認
docker exec naspi_restic restic -r /backup/repo check --read-data-subset=10%   # 2. 整合性
docker exec naspi_restic restic -r /backup/repo stats <ID> --mode restore-size # 3. 網羅性（項目数）
docker exec naspi_restic restic -r /backup/repo find <ファイル名>              # 4. ファイルを探す
docker exec naspi_restic restic -r /backup/repo restore <ID|latest> --target /tmp/restore --verify
docker exec naspi_restic restic -r /backup/repo restore <ID> --target /tmp/restore --include <パス> --verify
```

照合は `diff -r <元> <復元先>`（ディレクトリ）、または `sha256sum`（ファイル）で行う。
復元先には、元の場所と別の、通常のファイルシステム（ext4 など）を使う。exFAT では権限などを復元できない。

データ本体をすべて読む検査（`check --read-data`）は大容量では時間がかかる。定期的には `--read-data-subset=10%` のように
一部ずつ確認し、構成を変えたときなどに大きめの割合で確認する。

## 4. 障害時の復旧（手順。別環境での実施は未検証）

HDD の故障やサーバーの再構築などの後に、バックアップから復旧する手順。

必要なものは **リポジトリ（HDD の `repo` ディレクトリ）と、そのパスワードだけ**。パスワードを失うと誰も復元できないため、
`.env` とは別の安全な場所（パスワードマネージャーなど）にも保管する。

1. 復旧先のマシンに restic をインストールし、HDD をマウントする。
2. 同期を止める（bisync が復旧途中の状態をクラウドへ反映してしまうため）。
   ```
   docker compose stop rclone-sync
   ```
3. スナップショットを確認し、復元先（空のディレクトリ）へ復元する。
   ```
   restic -r <HDDのパス>/repo snapshots
   restic -r <HDDのパス>/repo restore <ID|latest> --target <復元先>
   ```
   特定のファイルだけなら `restic find` で世代を探し、その ID で `--include <パス>` を付ける。
4. 復元した内容を確認してから、`/mnt/data/cloud` へ戻す。
5. 同期を再開する（`docker compose start rclone-sync`）。

## 5. 運用上の注意

- **restic のコマンドをパイプで途中終了させない**（例: `restic ls ... | head`）。強制終了されたプロセスのロックが残り、
  以降の `check` などが「repository is already locked」で失敗する（実際に発生した）。
  バックアップ実行中でないことを確認して、`restic unlock` で古いロックだけを削除する（実行中のロックは削除されない）。
- **バックアップの実行中に元データが消えると、読めた分だけの不完全なスナップショットが保存される。**
  restic は一部が読めなくても、終了コード 3 でスナップショットを保存する。
  `backup.sh` は終了コード 3 のとき、そのスナップショットに `partial` タグを付け、`forget --prune` を行わず、
  実行履歴にも失敗として残す（`/log` で確認できる）。次に完全なバックアップが取れた時点で `partial` のものは削除されるため、
  不完全なスナップショットが世代として数えられ続けることはない。
  不完全なスナップショットは、網羅性の確認（3/4）で検出できる。
- 開発モードでは、`docker compose up -d` などでコンテナを作り直すと、実行中のバックアップや同期が中断される。

## 7. 調査記録: 不完全なスナップショット（2026-11-21）

**事象**: 開発環境のスナップショット `a38c91a0`（`/data`）が、クラウドの `00_Vault` の一部（430 ファイル）しか含んでいなかった
（クラウド上の `00_Vault` は 511 ファイル。他のフォルダは含まれていない）。

**原因（時刻の突き合わせによる推定）**: バックアップ実行中に、rclone のコンテナが停止した。

| 時刻 | 出来事 |
|---|---|
| 12:06:46 | バックアップ開始（クラウドを FUSE マウント経由で読む） |
| 12:24:04.97 | `docker compose up -d` により、旧 rclone・restic・Bot コンテナに停止シグナル |
| 12:24:05.05 | 旧 rclone コンテナが終了（FUSE マウントが切断） |
| **12:24:05.25** | **バックアップが終了し、スナップショットを保存**（rclone の終了の 0.2 秒後） |
| 12:24:14.98 | 旧 restic が SIGTERM に応答せず、強制終了 |

当時の restic のログはコンテナの作り直しで失われており、読み取りエラーを直接は確認できていない。
17 分半で約 860MB を読んでおり、FUSE 経由の読み取りは約 0.8MB/s だった。

**対応**: 網羅性の確認を復元テストに組み込んだ（手順 3/4）。開発モードのバックアップ対象を `/config` に変更済み。
